# AlphaAdopter — 엔지니어링 기록

무엇을 만들었는지보다 **왜 이렇게 만들었는지, 운영하면서 어떤 문제를 찾고 어떻게 고쳤는지**를
남기는 문서입니다. 수치는 모두 이 저장소의 커밋·문서·테스트에서 확인할 수 있는 실측값이며,
측정 조건(표본 크기, 환경)을 함께 적었습니다.

## 1. 한눈에 보기

AlphaAdopter는 사용자가 등록한 키워드·관심 종목의 뉴스를 수집해, 노이즈를 걸러내고
실시간으로 알려주는 서비스입니다. 2026년 9월부터 60개 이상의 PR로 아래 순서로 확장했습니다.

```
뉴스 소스 검증 → 도메인 설계 → 수집 파이프라인(Kafka/Mongo) → 실시간 알림(SSE/Redis)
→ AWS 인프라(EKS/RDS/Terraform) → 관측성·부하테스트(Prometheus/k6)
→ 인증(JWT) → AI 관련도 필터(Claude) → React 전환 → 백엔드 성능 개선
→ 임베딩 중복 제거(Voyage) → 보안 강화(RBAC·rate limit·쿠키) → AI 에이전트
→ 공급망 보안(Dependabot·CodeQL) → Flyway → 수집기 운영 보강
```

**주요 수치**

| 항목 | 결과 | 측정 조건 |
|---|---|---|
| AI 관련도 필터 | 알림 대상 30건 → 12건 (60% 감소) | 실제 수집된 알림 후보 30건(카카오·삼성전자·LG전자) |
| 관련도 판정 정확도 | 정밀도 78% → 100%, 재현율 100% | 직접 라벨링한 평가셋 20건(튜닝에 쓴 데이터와 동일) |
| API 부하테스트 | 12,278건, 실패율 0%, p95 18ms, HPA 1→3 파드 | k6 합성 트래픽, t3.small ×4 EKS |
| 백엔드 성능 개선 | N+1 2건, 트랜잭션 범위, 인덱스 6개, 커넥션 풀 | 코드 점검 후 수정 |
| 공급망 보안 | 운영 서버 내장 Tomcat critical CVE 3건 등 패치 | 의존성 그래프 제출 후 첫 스캔 |

## 2. 배경

정보가 넘칠수록 "원하는 정보를 얼마나 빠르고 정확하게 받는가"가 중요해집니다. Python으로
"뉴스 감지 → AI 중요도 판단 → 알림" 흐름을 먼저 검증한 뒤, 이 프로젝트에서는 같은 문제를
**Kotlin·Spring·Kafka·AWS로 실제 서비스처럼 설계·운영**하는 것을 목표로 했습니다. 기능을
만드는 데서 끝내지 않고, 배포한 뒤 측정하고, 문제를 찾아 고치는 과정을 남기는 것이 핵심입니다.

## 3. 아키텍처

```
[NAVER 뉴스 검색 API]
        │  최신순 수집 + 키워드별 수집 지점(누락 감지) + 분산 락(한 파드만 실행)
        ▼
  [수집기] ──▶ Kafka(news.raw) ──▶ [MongoDB: 원본 저장, link 유니크]
                                          │
                                          ▼
                     [매칭: 문자열 매칭 → 임베딩 중복 제거 → Claude 관련도 판단]
                                          │
                                          ▼
                          [PostgreSQL 저장] ─▶ Kafka(news.matched)
                                          │
                                          ▼
                         [알림: Redis Pub/Sub → SSE / 일일 다이제스트 메일]
                                          │
                                          ▼
                                 [React 클라이언트]
```

core-service·Kafka(Strimzi)·MongoDB는 EKS에, PostgreSQL·Redis는 RDS·ElastiCache에 두고
전부 Terraform으로 관리합니다. GitHub Actions가 OIDC로 AWS에 인증해 테스트 통과 후 배포합니다.

## 4. 기술적 의사결정

| 결정 | 이유 |
|---|---|
| 원본은 MongoDB, 정규화 데이터는 PostgreSQL | 소스마다 포맷이 다른 원본은 스키마 유연성이, 매칭·조회는 관계형 쿼리가 유리하다 |
| SSE (WebSocket 아님) | 알림은 서버→클라이언트 단방향이면 충분하다. 일반 HTTP라 ALB 뒤에서도 별도 처리가 필요 없다 |
| Kafka 컨슈머 → Redis Pub/Sub → SSE | 메시지를 소비한 파드와 사용자의 SSE 연결을 가진 파드가 다를 수 있다. Redis로 분리해 두어 HPA 확장 시 구조 변경 없이 그대로 동작했다 |
| 문자열 매칭 위에 Claude Haiku 2차 판단 | "카카오"처럼 일반명사로도 쓰이는 키워드는 문자열 매칭만으로 노이즈가 89%였다. 싼 필터로 후보를 줄인 뒤 AI를 호출해 비용을 통제한다 |
| AI·임베딩·rate limit은 장애 시 통과(fail-open) | 부가 기능의 장애가 알림 전달이나 로그인을 막는 단일 장애점이 되면 안 된다 |
| 다이제스트 메일 락은 장애 시 건너뜀(fail-closed) | 정보 전달과 달리 이미 보낸 메일은 되돌릴 수 없다. 작업의 성격에 따라 실패 정책을 다르게 둔다 |
| 분산 락·rate limit을 Redis로 직접 구현 | 이미 운영 중인 Redis로 충분한 규모라 ShedLock·bucket4j 같은 의존성을 늘리지 않았다 |
| JWT + httpOnly 쿠키, DB 기반 RBAC | 토큰을 스크립트에서 읽을 수 없게 하고, 관리자 권한은 DB 역할과 감사 로그로 관리한다 |
| GitHub Actions OIDC | 장기 액세스 키 없이 배포한다. 신뢰 범위를 이 저장소의 main 브랜치로 제한했다 |
| Flyway (`ddl-auto: validate`) | 스키마 변경을 SQL 파일로 명시하고, 엔티티와 스키마가 어긋나면 기동 시점에 실패하게 한다 |

## 5. 단계별 진행

### 0단계 — 뉴스 데이터 소스 검증
NAVER API HUB 뉴스 검색 API의 할당량(일 25,000회, 월 775,000회), 인증 헤더, 응답 포맷을
검증했습니다([`phase0-news-source-validation.md`](phase0-news-source-validation.md)). 이 할당량을
기준으로 고유 키워드 수 상한(15개)을 계산해 구독 API에 반영했습니다.

### 1~3단계 — 도메인, 수집 파이프라인, 실시간 알림
`User`·`Subscription`·`NewsArticle`(link 유니크)·`Notification`(MATCHED/SENT/FAILED)을 설계하고,
수집기 → Kafka → MongoDB 원본 저장 → PostgreSQL 정규화 → 구독 매칭 → Kafka → Redis Pub/Sub →
SSE로 이어지는 파이프라인을 만들었습니다. 프록시 유휴 타임아웃에 대비해 SSE 하트비트를 보냅니다.

### 4~5단계 — AWS 인프라와 관측성
VPC·RDS·ElastiCache·EKS를 Terraform으로 구성하고, `kube-prometheus-stack`으로 Prometheus·Grafana를
붙였습니다. k6 부하테스트 결과는 [`phase5-load-test-observability.md`](phase5-load-test-observability.md)에 있습니다.

### 6·8단계 — AI 관련도 필터와 임베딩 중복 제거
Claude Haiku로 기사와 키워드의 관련도를 0~100점으로 판단하고, 구조화 출력(tool use)·프롬프트
인젝션 방어·Redis 캐싱·429 재시도·Micrometer 계측을 갖췄습니다. 평가셋으로 정밀도·재현율을 재며
오탐 패턴을 찾아 프롬프트를 개선했습니다([`phase6-ai-relevance-filtering.md`](phase6-ai-relevance-filtering.md)).
같은 사건의 중복 보도는 Voyage AI 임베딩의 코사인 유사도로 묶습니다([`phase8-embedding-dedup.md`](phase8-embedding-dedup.md)).

### 7단계 — React 전환과 백엔드 성능 개선
바닐라 JS 화면을 React + TypeScript + Vite로 다시 작성하고, 운영 관점에서 백엔드를 점검해 성능
문제 5건을 고쳤습니다(8절).

### 이후 — 보안 강화, AI 에이전트, 공급망 보안, 수집기 운영 보강
9~11절에 정리했습니다.

## 6. 문제 해결 기록

### 수집기를 운영 관점에서 다시 점검해 찾은 문제 5건

"뉴스가 빠지거나 두 번 처리될 수 있는 경로가 있는가"를 기준으로 수집기를 다시 점검했습니다.

| 문제 | 원인 | 조치 |
|---|---|---|
| 최신 기사를 놓침 | 정렬 파라미터 없이 요청해 API 기본값인 정확도순으로 받고 있었다 | `sort=date`로 최신순 수집 |
| 기사가 몰리면 조용히 누락 | 1분마다 키워드당 10건만 받고 어디까지 받았는지 기억하지 않았다 | 키워드별 수집 지점(`collector_checkpoints`)까지 최대 3페이지(300건)를 따라가고, 그래도 못 닿으면 누락 의심으로 기록 |
| 실패가 흔적 없이 사라짐 | 예외를 로그 한 줄로 삼키고, Kafka 발행 결과도 확인하지 않았다 | 429·5xx·네트워크 오류만 지수 백오프로 재시도, 발행 실패 시 수집 지점을 전진시키지 않아 다음 주기에 재수집, 이상 상황은 `collector_incidents`에 기록 |
| **HPA로 파드가 늘면 같은 작업이 파드 수만큼 실행** | `@Scheduled`는 파드마다 각자 돈다. 파드 3개면 API 할당량을 3배로 쓰고, 다이제스트 메일이 중복 발송될 수 있었다 | Redis `SET NX` 분산 락. 작업이 빨리 끝나도 주기의 80% 동안 락을 유지해, 시계가 어긋난 다른 파드가 직후에 다시 실행하지 못하게 했다 |
| 원본이 계속 중복 저장 | MongoDB 원본 저장이 무조건 insert였다 | `link` 유니크 인덱스 + upsert로 재수집·Kafka 재전달에도 한 건만 저장 |

평소에는 키워드당 한 번의 호출로 수집 지점에 닿기 때문에 API 사용량은 예전과 같고, 기사가 몰릴
때만 추가로 호출합니다. 정상 수집은 지표(`news.collector.*`)로, 사람이 확인해야 하는 이상만 테이블로
남겨 관리자 화면에서 확인합니다. 페이지 순회·누락 감지·발행 실패 처리는 단위 테스트로, 분산 락과
중복 저장 방지는 실제 Redis·MongoDB(Testcontainers)로 검증했습니다.

### 인프라·배포

**GitHub Actions OIDC 인증 실패** — 저장소 이름이 바뀐 이력이 있어, GitHub이 발급하는 토큰의
`sub` 클레임이 이름이 아니라 불변 숫자 ID를 포함한 형태로 나오고 있었습니다. 실제 발급된 토큰을
디버그 단계에서 출력해 확인하고, IAM 신뢰 정책 조건을 ID 기반으로 바꿔 이름이 다시 바뀌어도
깨지지 않게 했습니다.

**Kafka 파이프라인이 처음부터 동작하지 않던 문제** — `spring-kafka`만 추가돼 있어 Spring Boot
자동 설정이 붙지 않았고, Jackson 3 프로젝트에서 직렬화 설정이 Jackson 2 클래스를 가리키고 있었습니다.
로컬 인프라를 띄워 실제로 실행해 보고 발견해, 스타터와 직렬화 설정을 교체했습니다.

**NAVER API 응답 파싱 실패와 MongoDB 설정 누락** — API가 JSON을 `text/plain`으로 내려줘 파싱이
거부되고 있었고, Spring Boot 4.1에서 MongoDB 설정 키가 `spring.data.mongodb`에서 `spring.mongodb`로
바뀐 탓에 기본 주소로 접속을 시도하며 파이프라인이 멈춰 있었습니다. 둘 다 수정했습니다.

**CI/CD가 매니페스트 변경을 반영하지 않던 문제** — `kubectl set image`로 이미지 태그만 바꾸고
있어 Service·ServiceMonitor 변경이 클러스터에 적용되지 않았습니다. 배포 단계에서 매니페스트를
`apply`하도록 바꿨습니다.

**EKS 배포 역할의 CRD 권한 누락, Grafana 볼륨 Multi-Attach** — `AmazonEKSEditPolicy`가
ServiceMonitor 같은 커스텀 리소스를 다루지 못해 해당 CRD에만 권한을 주는 ClusterRole을 추가했고,
RWO 볼륨을 쓰는 Grafana는 배포 전략을 `Recreate`로 고정했습니다.

### 테스트 인프라

**Testcontainers 도입** — 2.x의 아티팩트명 변경, `apache/kafka` 이미지와 대기 전략 불일치,
MongoDB URI 구성, 테스트 트랜잭션 안에서 만든 데이터를 별도 스레드의 Kafka 컨슈머가 보지 못하는
문제, 클래스별 컨테이너 종료로 다른 테스트가 깨지는 문제를 각각 해결하고 싱글턴 컨테이너 패턴으로
정리했습니다.

**개발자 환경변수에 따라 결과가 달라지던 테스트** — 로컬에 Claude API 키가 있으면 통합 테스트의
합성 문구가 실제 AI 판단으로 걸러졌습니다. 해당 테스트는 AI를 명시적으로 끄도록 고정했습니다.

**캐시 테스트가 CI에서 계속 실패하던 문제** — `Cache.evict`는 계약상 실제 삭제를 늦게 수행해도
되는 메서드라, 트랜잭션 안에서 캐시를 비운 직후 값이 남아 있었습니다. 즉시 삭제를 보장하는
`evictIfPresent`로 바꿔 테스트가 의도를 정확히 검증하게 했습니다.

### 애플리케이션

**모든 에러 응답이 403으로 가려지던 문제** — `ResponseStatusException`이 `/error`로 내부 포워딩될 때
그 경로가 인증 대상이어서 실제 상태 코드(409, 401 등)가 403으로 덮였습니다. `/error`를 허용했습니다.

**SSE 연결이 "연결 중"에서 멈추던 버그 2건**
1. SSE의 비동기 재디스패치가 다른 스레드에서 실행되면 스레드 로컬인 `SecurityContext`가 비어,
   인가가 실패하고 커넥션이 조용히 끊겼습니다. 비동기 디스패치에도 인증 필터를 적용했습니다.
2. EventSource 연결과 인증된 요청이 동시에 나가는 페이지 진입 패턴에서 Tomcat이 첫 플러시를
   미뤘습니다. 연결 직후 초기 이벤트를 보내 강제로 플러시하고, 재현 스크립트로 전후를 확인했습니다.

**구독 캐시 도입 후 드러난 레이스 컨디션** — 구독 생성 직후, 캐시가 갱신되기 전에 매칭될 뉴스가
먼저 소비되면 매칭을 영구히 놓칠 수 있었습니다. 저장 직후 캐시를 즉시 갱신하는 경로로 통일했습니다.

## 7. 프론트엔드

빌드 도구 없는 HTML/JS로 시작해 화면을 빠르게 붙였고, 사이드바·상태 관리가 늘면서 React 18 +
TypeScript + Vite로 다시 작성했습니다(현재 React 19). 컴포넌트 단위 구조, 타입이 있는 API
클라이언트, vitest 테스트를 갖추고, 프론트엔드 빌드를 Docker 멀티스테이지 빌드와 CI/CD에 통합했습니다.
코드만 보고 UI를 판단하지 않도록, 헤드리스 브라우저로 실제 렌더링 스크린샷을 찍어 확인하는 절차를
두었습니다.

## 8. 백엔드 성능 개선

커넥션 풀, 캐싱, N+1, 인덱싱 네 가지 관점으로 백엔드를 점검해 실제 문제 5건을 고쳤습니다.

1. 뉴스 1건마다 구독 테이블 전체를 읽던 것을 메모리 캐시(`SubscriptionCache`, 30초 주기 + 변경 시
   즉시 갱신)로 교체
2. 느린 외부 AI 호출을 `@Transactional` 범위 밖으로 분리해, 호출하는 동안 DB 커넥션을 붙잡지 않게 함
3. 사용자 목록에서 사용자마다 따로 실행하던 COUNT 쿼리(N+1)를 `GROUP BY` 한 번으로 교체
4. 구독·알림 테이블에 인덱스 6개 추가 (PostgreSQL은 FK 컬럼에 인덱스를 자동으로 만들지 않음)
5. HikariCP 풀 설정을 명시 (Kafka 컨슈머·스케줄러·웹 요청이 같은 풀을 공유하는 구조)

## 9. AI 에이전트 — 단발성 판단에서 멀티스텝 조사로

관련도 필터와 임베딩 중복 제거는 "한 번 묻고 한 번 답 받는" 호출이었습니다. 관리자가 특정 사용자의
활동이 정상인지 조사할 때는 가입일을 보고, 그 결과에 따라 구독 패턴을 더 볼지 정하고, 알림 열람
패턴까지 종합해야 합니다. 이렇게 중간 결과를 보고 다음 행동을 정하는 문제를 위해, 모델이
관찰 → 도구 호출 → 재관찰을 반복하다 스스로 결론을 내는 에이전트 루프(ReAct)를
`UserInvestigationAgent`로 구현했습니다.

- **목적**: 가입 직후 키워드를 대량 등록해 API 할당량을 소진시키는 계정, 알림을 전혀 열지 않는
  계정 같은 이상 사용을 위험도(LOW/MEDIUM/HIGH)와 근거, 권장 조치로 보고
- **도구 3개는 모두 읽기 전용**: 가입 정보, 구독 활동, 알림 열람률. 계정 조치는 에이전트가 하지
  않고 항상 관리자가 결정
- **결론은 `report_verdict` 도구로만 받음**: 자유 텍스트를 해석하는 대신 형식을 강제해 파싱을 단순화
- **최대 5회 반복**: 결론 없이 도구만 반복하면 강제 종료하고 판단 불가(INCONCLUSIVE)로 처리
- **프롬프트 인젝션 방어**: 사용자가 입력한 키워드를 `<data>` 구분자로 감싸 지시로 해석되지 않게 함
- **평가 하네스**: 정상, 구독 폭주, 실사용 없음, 신규 가입(오탐 방지용) 4가지 시나리오를 실제 DB에
  넣고 판단을 확인하는 `UserInvestigationEvalReport`. 표본이 작아 통과/실패 판정 대신 근거까지
  사람이 읽는 리포트로 둠

## 10. 보안 강화

| 항목 | 내용 |
|---|---|
| 토큰 보관 | access token을 60분으로 줄이고, refresh token은 Redis에 SHA-256 해시로 저장(교체·즉시 폐기 지원). 저장 위치를 `localStorage`에서 httpOnly + `SameSite=Strict` 쿠키로 옮겨 XSS 노출 차단 |
| 권한 | 환경변수 화이트리스트에서 DB 기반 RBAC로 전환. `/api/admin/**`은 게이트웨이(SecurityConfig)와 컨트롤러에서 이중으로 검사하고, 권한 변경은 `admin_audit_logs`에 기록 |
| 남용 방지 | 회원가입·로그인·구독 생성에 IP 기준 rate limit(Redis), 초과 시 429 + `Retry-After` |
| 캐시와 인가 | 관리자 통계 캐시보다 인가 검사를 앞에 두어 캐시 히트가 인가를 우회하지 못하게 함 |
| 의존성 취약점 | PR마다 새 의존성 검사(dependency-review), 매주 기존 의존성 검사(Dependabot) |
| 백엔드 의존성 가시성 | Gradle 버전이 Spring Boot BOM으로 관리돼 스캐너가 백엔드를 아예 못 보고 있었다. 실제 해석된 의존성 그래프를 제출하게 하자 운영 서버 내장 Tomcat의 critical CVE 3건(인가 우회 2, DIGEST 재전송 1)이 바로 드러났고, BOM이 일반 constraints를 덮어쓰는 문제를 `tomcat.version` 프로퍼티로 우회해 패치. jackson-core, lz4-java, snappy-java도 같은 방식으로 패치 |
| 코드 취약점 | CodeQL로 Kotlin·TypeScript 코드를 PR·main·매주 스캔. CI에서 Kotlin 컴파일러 데몬과 CodeQL 추적이 충돌해 멈추던 문제를 in-process 컴파일과 JVM 메모리 설정으로 해결 |
| 스코프 | 자본시장법상 유사투자자문업으로 해석될 수 있는 투자 조언·매매 신호 기능은 제외. 뉴스 본문은 저장하지 않고 제목·요약·링크만 다룸 |

## 11. 알고 있는 한계와 다음 단계

- **평가 데이터 규모**: 관련도 평가셋은 20건이고, 개선 후 수치는 튜닝에 쓴 같은 데이터 기준입니다.
  실제 수집 기사로 100건 이상을 라벨링하고 튜닝용·검증용을 분리해 다시 측정할 계획입니다.
- **알림 도착 시간**: 현재 60초 주기 폴링이며, 기사 게시부터 알림 도착까지의 지연은 아직 측정하지
  않았습니다. 수집기에 기사 시각이 남으므로 이를 기준으로 지연 분포를 측정할 예정입니다.
- **부하테스트 범위**: k6 결과는 구독 API에 대한 합성 트래픽이며, 알림 파이프라인 전체 부하는 아닙니다.
- **에이전트 평가**: 4개 시나리오는 동작 확인용이며 정확도를 말할 수 있는 규모가 아닙니다.
