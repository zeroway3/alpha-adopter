# 사용자 조사 에이전트 평가

`UserInvestigationAgent`가 관리자가 지목한 사용자를 조사해 이상 사용(외부 API 할당량을 위협하는 구독 폭주,
실사용 없는 계정)을 맞게 판단하는지 실제 Claude API(claude-haiku-4-5)로 측정한 기록입니다.
재현: `ANTHROPIC_API_KEY=... AGENT_EVAL_RUNS=5 ./gradlew test --tests '*UserInvestigationEvalReport'`
(결과는 `core-service/build/reports/agent-eval.md`).

## 평가 방법

- **시나리오 20개**를 실제 DB에 심고 에이전트에게 사용자 ID만 준다. 에이전트는 조회 도구 3개를 스스로 골라 호출한다.
- **튜닝용 10개 / 검증용 10개 분리**: 튜닝용은 결과를 보고 도구·프롬프트를 고치는 데 썼다. 검증용은 결과를 보기
  전에 기대값을 먼저 정했고, 개선에 쓰지 않았다. **성능 보고 수치는 검증용 결과**다.
- 각 시나리오를 **5회 반복**해 판정이 흔들리는지(일관성)도 본다. MEDIUM/HIGH는 '의심', LOW/INCONCLUSIVE는 '정상'.
- 정확도에는 표본이 작을 때 쓰는 **Wilson 95% 신뢰구간**을 함께 적는다.
- 시나리오 키워드는 실제 종목명을 쓴다(아래 2단계 참고).

## 결과 요약

| 세트 | 정확도 | 95% 신뢰구간 | 오탐 | 미탐 | 다수결 정확도 | 일관성 |
|---|---|---|---|---|---|---|
| **검증용** | **98% (49/50)** | **90~100%** | 1 | **0** | 10/10 | 9/10 |
| 튜닝용 | 94% (47/50) | 84~98% | 0 | 3 | 10/10 | 8/10 |

조사 1건당 도구 호출 평균 2회, 소요 시간 p50 10.8초 / p95 12.2초, 토큰 입력 약 5,900·출력 약 1,100,
비용 약 $0.011.

## 개선 과정 (튜닝용 시나리오, 각 3회)

| 단계 | 정확도 | 오탐 | 미탐 | 무엇을 바꿨나 |
|---|---|---|---|---|
| 0. 첫 실측 | 0% | - | - | 모든 요청이 400으로 실패. 요청 직렬화 버그(아래) |
| 1. 직렬화 수정 | 87% | 4 | 0 | 쓰지 않는 블록 필드(`"id": null` 등)를 보내지 않도록 수정 |
| 2. 키워드 힌트 제거 | **77%** | 4 | 3 | 시나리오 키워드가 "자동0~9", "급증0~13"이라 모델이 시간 패턴이 아니라 이름을 보고 맞힌 것을 발견. 실제 종목명으로 바꾸자 점수가 떨어짐 |
| 3. 표본 부족 규칙 | 83% | 2 | 3 | 알림 3건을 안 읽은 7일차 사용자를 반복 오탐. 개인화 점수와 같은 "5건 미만이면 참여도로 판단하지 않음" 규칙을 도구 결과에 명시 |
| 4. 최근 몰린 구독 노출 | 90% | 3 | 0 | 30일 된 계정이 오늘 몇 초 만에 14개를 구독한 경우를 3번 다 놓침. 도구가 "최초~최근 간격(30일)"만 줘서 폭주가 가려졌음. 최근 24시간 구독 수와 60초 안 최대 구독 수를 추가 |
| 5. 서비스 정책 명시 | 94% (5회) | 0 | 3 | 가입 직후 종목 3개 등록을 의심하는 오탐. 시스템 프롬프트에 역할만 있고 "무엇이 어뷰징인지"가 없었음. 할당량·구독 한도 근거와 정상 기준을 정책으로 명시 |

## 찾은 문제와 배운 것

- **스텁 테스트만으로는 실제 API 계약을 검증할 수 없다.** 에이전트는 가짜 응답으로 만든 단위 테스트를 전부 통과했지만,
  실제 API에서는 첫 요청부터 400(`messages.0.content.0.text.id: Extra inputs are not permitted`)으로 실패하고 있었다.
  응답만 흉내 내고 요청 본문을 검사하지 않았기 때문이다. 요청 본문에 null 필드가 없는지 검사하는 회귀 테스트를 추가했다.
- **평가 데이터에 정답 힌트가 섞이면 점수가 부풀려진다.** 더미 키워드 이름만으로 87%가 나왔고, 실제 종목명으로 바꾸자 77%였다.
- **모델이 못 맞히는 원인이 모델이 아닐 수 있다.** 놓친 3건은 도구가 집계 과정에서 폭주를 지워 버린 탓이었다. 모델이 볼 수
  없는 패턴은 프롬프트로 고칠 수 없다.
- **조정에는 비용이 따른다.** 5단계 정책 명시 뒤 "10초 안에 10개"(한도 15의 2/3) 시나리오는 5회 중 2회를 LOW로 판단했다.
  "한도에 가까운 수"라는 기준이 경계에서 흔들린다는 뜻이다.

## 한계

- 시나리오는 사람이 설계한 합성 데이터다. 실제 어뷰징 계정 로그로 검증한 것은 아니다.
- 검증용 10개는 규모가 작아 신뢰구간이 넓다(90~100%). 새 시나리오를 계속 추가해야 한다.
- 이분화(의심/정상) 기준으로 평가했고, MEDIUM과 HIGH의 구분이 맞는지는 평가하지 않았다.

## 사용자 조사 에이전트 평가

모델 판정이 MEDIUM/HIGH면 '의심', LOW/INCONCLUSIVE면 '정상'으로 보고 시나리오의 기대값과 비교했다. **성능 보고 수치는 검증용 결과**이고, 튜닝용은 개선 과정 추적용이다.
