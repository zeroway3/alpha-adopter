# 8단계 — 임베딩 기반 기사 중복 제거

## 문제

6단계에서 AI 관련도 판단으로 "무관한 기사"는 걸러냈지만, "같은 사건을 다룬 서로 다른
기사"는 여전히 걸러지지 않는다. 하나의 사건(예: 특정 기업의 실적 발표)이 여러 언론사에서
각자 다른 제목·문장으로 보도되면, 각 기사가 문자열 매칭과 AI 관련도 판단을 개별적으로
통과해 사용자에게 사실상 동일한 알림이 여러 번 나가게 된다.

## 해결

Voyage AI 임베딩으로 기사 제목+본문을 벡터화하고, 최근 기사들과의 코사인 유사도를 비교해
"표현은 다른데 사실상 같은 기사"를 감지한다(`ai/VoyageEmbeddingClient.kt`,
`ai/NewsDeduplicationService.kt`). Claude 자체에는 임베딩 엔드포인트가 없어(Anthropic
공식 문서도 임베딩이 필요하면 Voyage AI를 권장한다) 별도 서비스를 연동했다.

### 왜 별도 벡터 DB 없이 Redis로 처리했는가

pgvector 같은 벡터 DB를 새로 도입하는 대신, 이미 SSE Pub/Sub·관리자 통계 캐시로 쓰고
있는 Redis에 최근 N시간(기본 48시간)짜리 슬라이딩 윈도우를 뒀다 — 정렬집합(ZSet)에
`(링크, 타임스탬프)`를, 별도 키에 `링크 → 벡터(JSON)`를 저장하고, 새 기사가 들어오면
윈도우 안의 후보와 브루트포스로 코사인 유사도를 계산한다. 이 프로젝트 규모(구독 키워드
최대 15개, 60초 폴링)에서는 윈도우 안 후보가 최대 수백 건 수준이라, 새 인프라를 추가하는
비용 대비 이 방식으로 충분하다고 판단했다.

### 언제 임베딩을 호출하는가

문자열 매칭을 통과한(=알림 후보인) 기사에 대해서만 중복 검사를 수행한다. 애초에 어떤
구독 키워드와도 매칭되지 않는 기사는 알림 후보가 아니므로, 그런 기사까지 임베딩을
계산하는 건 불필요한 API 호출이다. 이 순서 덕분에 중복으로 판정된 기사는 Claude 관련도
판단(비용 발생)과 알림 발행까지 함께 스킵되어, 6단계 AI 호출 비용도 같이 줄어든다.

### 안전 장치

- `VOYAGE_API_KEY`가 설정되지 않으면 자동으로 비활성화되고 기존처럼 중복 검사 없이
  동작한다(6단계 `ANTHROPIC_API_KEY`와 동일한 원칙)
- 임베딩 호출이 실패하면 안전하게 "중복 아님"으로 처리한다(fail-open) — 임베딩 인프라
  장애가 알림 파이프라인 전체를 막는 장애점이 되면 안 된다
- Claude API와 동일하게 429 지수 백오프 재시도 적용
- Micrometer로 중복 감지율(`news.dedup`, result=duplicate/unique)을 계측해 기존
  Prometheus+Grafana 스택에 노출

## 테스트

`VoyageEmbeddingClientStubTest`(응답 파싱·재시도), `NewsDeduplicationServiceTest`
(유사도 판정·fail-open·윈도우 등록)를 MockRestServiceServer + Mockito로 실제 네트워크·
Redis 없이 검증한다. `NewsMatchingPipelineIntegrationTest`는 `VOYAGE_API_KEY`가 없는
기본 환경에서 실행되므로, 중복 검사가 자동 비활성화된 상태에서도 기존 문자열 매칭
파이프라인이 그대로 동작함을 함께 확인한다.

## 앞으로

지금은 20건 규모의 수동 테스트만 거쳤다. 실제 서비스에서 같은 사건을 다룬 여러 기사가
수집됐을 때 유사도 임계값(기본 0.90)이 실제로 적절한지는, 6단계의 eval 데이터셋처럼
실제 중복/비중복 기사 쌍을 사람이 라벨링해 검증하는 과정이 필요하다.
